# Скоринговая модель

Отчёт о разработке модели кредитного скоринга (тестовое задание)

**Версия модели:** RandomForestClassifier (pipeline v1)
**Дата:** 14.08.2026

---

## 1. Резюме

Проект реализует модель бинарной классификации заёмщиков на «плохих» (`bad`) и «хороших» (`good`) по данным кредитной заявки, а также REST API на `Flask` для обучения модели и получения предсказаний. Итоговая модель — `RandomForestClassifier` в составе `sklearn`-пайплайна с предобработкой признаков и отбором лучших гиперпараметров через `GridSearchCV`. Качество на отложенной тестовой выборке: **AUC-ROC ≈ 0.87** (на кросс-валидации ≈ 0.82).

## 2. Постановка задачи

Банку требуется автоматизированный инструмент оценки риска по заявке на кредит: на основе кредитной истории, данных о просрочках, обеспечении и социально-демографических характеристик заявителя модель должна оценивать вероятность того, что заёмщик окажется «плохим» (нарушит условия обслуживания долга). Задача — бинарная классификация с выдачей класса (`0`/`1`) и вероятности отнесения к классу `bad`. Предсказание используется как вспомогательный сигнал при принятии решения по заявке, а не как автоматическое одобрение/отказ.

## 3. Описание входных данных

- **Источник:** файл `data/data.xlsx`, единица наблюдения — одна кредитная заявка.
- **Объём выборки:** 2565 записей, 56 исходных столбцов (включая идентификатор заявки и целевую переменную).
- **Целевая переменная:** `Маркер`, принимает значения `good` / `bad`, кодируется в `1` (bad) / `0` (good) в `load_and_process_data`.
- **Баланс классов:** `good` — 2357 записей (91.9%), `bad` — 208 записей (8.1%). Выборка сильно несбалансирована в пользу «хороших» заёмщиков.
- **Пропуски и дубликаты:** пропущенных значений в исходных данных не обнаружено.
- **Типы признаков:** 36 числовых целочисленных, 2 числовых вещественных, 18 категориальных (текстовых), не считая идентификатора и целевой переменной.
- **Отсеиваемые при обработке столбцы:** `Номер_заявки`, `Мобильный_телефон`, `Кредитов_всего`, `Совпадение_адреса_прописки_и_регистрации`, `Домашний_телефон`, `Страна_рождения` — исключаются как неинформативные, дублирующие или технические.
- **Итоговый набор признаков модели:** 49 (полный список — см. Приложение 12.1 / `constants.ORDER_COLUMNS`).

Признаки группируются по смысловым блокам:

1. **Кредитная история и активность по кредитам** — количество кредитов за последние 3/6 месяцев, количество запросов кредитной истории (за 30 дней и всего), количество закрытых кредитов (всего и за год).
2. **Просрочки** — по продолжительности (последняя просрочка, наибольшая просрочка за год и за весь период) и по типу обязательства (основной долг, проценты, платежи), разбитые на интервалы 1–7, 8–30, 31–90, 91–180 и более 180 дней.
3. **Обеспечение** — общее количество договоров обеспечения, закрытые и действующие договоры.
4. **Юридическая история** — привлечения к административной и уголовной ответственности.
5. **Социально-демографические данные** — пол, возраст, семейное положение, количество детей (в т.ч. несовершеннолетних), образование, профессия, вид занятости.
6. **Контактные данные и имущество** — наличие рабочего телефона, телефонов по месту работы/бухгалтерии, объекты недвижимости, транспортные средства.
7. **География** — тип населённого пункта регистрации и проживания.
8. **Прочее** — месяц создания заявки, рабочий стаж, показатель кредитной нагрузки.

## 4. Наблюдения по составу данных

Без углублённого разведочного анализа (EDA) можно выделить следующие исходные характеристики выборки, значимые для дизайна модели:

- Сильный дисбаланс классов (~8% «плохих» заёмщиков) — учтён через стратификацию при разбиении на train/test и через метрику AUC-ROC, устойчивую к дисбалансу.
- Смешанный тип данных (числовые и категориальные признаки) — потребовал раздельной предобработки в `ColumnTransformer`.
- Большое число признаков (49) с потенциальной избыточностью/коррелированностью (особенно среди детализированных признаков просрочек) — обусловило включение шага отбора признаков (`SelectKBest`) в пайплайн.
- Отсутствие пропусков упростило пайплайн предобработки (не потребовались импутеры).

## 5. Предобработка и feature engineering

Предобработка реализована как единый `sklearn`-пайплайн (`model_functions.fit_and_save_model`):

1. **Кодирование категориальных признаков** — `OrdinalEncoder` с обработкой неизвестных категорий (`handle_unknown='use_encoded_value', unknown_value=-1`).
2. **Масштабирование числовых признаков** — `MinMaxScaler`.
3. **Отбор признаков** — `SelectKBest(score_func=chi2)`, число отбираемых признаков `k` подбирается в диапазоне 20–35 либо используется весь набор (`'all'`) как гиперпараметр модели.
4. **Разбиение на выборки** — `train_test_split` с параметрами `test_size=0.20`, `stratify=y`, `random_state=42` (см. `constants.py`).

## 6. Архитектура модели

Модель оформлена как единый объект `Pipeline`:

```
Pipeline([
    ('preprocessor', ColumnTransformer([...])),   # кодирование + масштабирование
    ('feature_selector', SelectKBest(chi2)),       # отбор признаков
    ('models', RandomForestClassifier)             # классификатор
])
```

**Алгоритм:** `RandomForestClassifier` — выбран как устойчивый к разнородным признакам и выбросам ансамблевый метод, не требующий сложной калибровки и дающий приемлемую интерпретируемость через важность признаков.

**Подбор гиперпараметров:** `GridSearchCV` по сетке:

- `models__max_depth`: 5–7;
- `models__n_estimators`: 100, 150;
- `feature_selector__k`: 20–35 либо `'all'`.

**Схема валидации:** 3-фолдовая кросс-валидация (`cv=3`), целевая метрика — `roc_auc`.

## 7. Результаты обучения и валидации

По последнему проведённому обучению (лог сервиса):

| Метрика | Значение |
|---|---|
| AUC-ROC, кросс-валидация (лучшая комбинация гиперпараметров) | 0.8164 |
| AUC-ROC, тестовая выборка | 0.8665 |

Разрыв между CV и test в пределах ожидаемого шума на выборке такого объёма и не указывает на выраженное переобучение. Лучшие гиперпараметры фиксируются в логе обучения (`gs.best_params_`) при каждом запуске `/train_model`, так как повторное обучение на новых данных может дать иную комбинацию.

*Примечание: числа выше зафиксированы кодом/логами проекта; при переобучении модели на актуальных данных значения нужно обновить.*

## 8. Ограничения и риски модели

- **Дисбаланс классов** — при доле «плохих» заёмщиков ~8% высокий AUC-ROC не гарантирует высокую полноту (recall) по классу `bad`; для операционного использования стоит дополнительно контролировать precision/recall и подбирать порог отсечения под бизнес-требования.
- **Интерпретируемость** — `RandomForest` менее прозрачен, чем логистическая регрессия/скоркарта; для банковского комплаенса может потребоваться дополнительное объяснение решений (например, через feature importance или SHAP).
- **Дрейф данных** — модель обучена на исторической выборке; изменение макроэкономических условий или профиля заявителей потребует периодического переобучения и мониторинга качества.
- **Отсутствие защиты от рассинхронизации признаков** — `/get_predicts` требует точного соответствия названий признаков `constants.ORDER_COLUMNS`; ошибки в названиях не валидируются явно.
- **Оценка только по AUC-ROC** — для более полной картины качества рекомендуется дополнительно считать Gini, confusion matrix, precision/recall на бизнес-значимом пороге.

## 9. Развёртывание и эксплуатация

### Структура проекта

- `/data` — данные для обучения модели (файл `.xlsx`, обязательно называется `data`).
- `/models` — папка для сохранённого объекта модели (создаётся эндпоинтом `/train_model`, файл `model.pkl`).
- `app.py` — Flask-приложение и объявление эндпоинтов.
- `constants.py` — константы сервиса (порт, random_state, размер тестовой выборки, порядок признаков).
- `model_functions.py` — функции загрузки/обработки данных, обучения, сохранения и инференса модели.
- `Dockerfile` — сборка образа для деплоя.
- `logs` — лог-файл работы приложения.
- `requirements.txt` — зависимости проекта.

### API

**`GET /health`** — проверка работоспособности сервиса.

```python
import requests
url = 'http://127.0.0.1:9119'
response = requests.get(url=f'{url}/health')
response.json()
# {'API Status': 'API service for the model is running and working correctly.'}
```

**`GET /train_model`** — загрузка данных из `/data`, подбор гиперпараметров, обучение и сохранение модели в `/models/model.pkl`. Возвращает значения AUC-ROC на кросс-валидации и тесте.

```python
import requests
url = 'http://127.0.0.1:9119'
response = requests.get(url=f'{url}/train_model')
response.json()
# {'Status': 'The model was trained and saved. AUC-ROC on CV = 0.8164, on test = 0.8665.'}
```

**`POST /get_predicts`** — получение предсказания по одной заявке. На вход — JSON с признаками (порядок не важен, названия должны совпадать с `constants.ORDER_COLUMNS`). На выходе — класс (`label`) и вероятность класса `bad` (`proba`).

```python
import requests, json
url = 'http://127.0.0.1:9119'
data = {
    'Месяц_создания_заявки': 'autumn',
    'Количество_кредитов_за_последние_3_месяцa': 1,
    # ... остальные признаки, полный список — Приложение 12.1
    'Возраст': 27,
    'Рабочий_стаж': 1.0,
    'Кредитная_нагрузка': 0.29310877883186837,
}
response = requests.post(url=f'{url}/get_predicts', json=data)
response.json()
# {'label': '0', 'proba': '0.1241563866236885'}
```

Если модель ещё не обучена (нет `models/model.pkl`), эндпоинт вернёт предупреждение:

```python
{'Warning': "This is the first launch of the application - there aren't any model files in the app directory. You have to run the '/train_model' endpoint first of all to get pre-trained models to use."}
```

### Инструкция по запуску

1. (Опционально) создать файл `.env` с переменной `PROD_HOST` — порт сервиса (по умолчанию `9119`).
2. Клонировать репозиторий: `git clone https://creds@github.com/AlexGribPython/BGPBTestTask.git` (`creds` предоставляются отдельно).
3. Собрать образ: `docker build -t image_name .`
4. Запустить контейнер: `docker run -p 9119:9119 image_name`.

## 10. Мониторинг и дальнейшее развитие

- Отслеживать AUC-ROC / Gini на новых данных после каждого переобучения, фиксировать историю метрик по версиям модели.
- Ввести дополнительный контроль качества по классу `bad` (recall/precision на выбранном пороге), так как AUC-ROC не отражает поведение модели на конкретном операционном пороге.
- Настроить логирование входных признаков предсказаний для последующего анализа дрейфа данных.
- Рассмотреть добавление автоматической валидации входного JSON в `/get_predicts` (проверка наличия и типов всех признаков из `ORDER_COLUMNS`).
- Периодически пересматривать список признаков и целесообразность SelectKBest/chi2 как метода отбора, в том числе сравнить с альтернативными алгоритмами (градиентный бустинг, логистическая регрессия со скоркартой) для повышения интерпретируемости.
